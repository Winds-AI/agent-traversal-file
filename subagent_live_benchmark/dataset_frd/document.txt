# 1. FRD Overview
This FRD defines functional and non-functional requirements for ProcureSphere Cloud, a SaaS procurement and AP automation product.
The product target is multi-entity organizations with centralized finance and distributed requesters.
The document is written for product managers, engineering teams, QA, implementation consultants, and customer success teams.
Every module section includes page layout, form fields, workflow behavior, permissions, validations, edge cases, notifications, reports, and integration impacts.
All requirements are for web application v1 unless explicitly labeled as future scope.
The baseline process map is described in {@process-map}.
Core role semantics are defined in {@role-catalog} and enforcement rules in {@permission-model}.
Cross-cutting field and validation conventions are centralized in {@global-form-standards}.
Cross-cutting NFR requirements are defined from {@nfr-performance} through {@nfr-disaster-recovery}.
Migration, rollout, and support requirements are covered in {@data-migration-strategy}, {@rollout-plan}, and {@support-operations}.
The document uses requirement labels in the format REQ-<AREA>-<NUMBER> to support traceability.


# 2. Product Domain Context
ProcureSphere Cloud is a B2B SaaS platform for source-to-pay operations.
Typical customer profile is 500 to 20,000 employee organizations with 2 to 80 legal entities.
Target industries include healthcare networks, manufacturing groups, retail chains, and technology services firms.
Customers typically run ERP or accounting systems that are strong in GL but weak in operational procurement controls.
The platform provides a policy-governed workflow from request to payment with full auditability.
The product must support central procurement teams and local site-level cost center owners.
The platform assumes customers have an existing identity provider and downstream finance system.
The platform does not replace ERP as the financial system of record; it orchestrates operational controls and syncs accounting postings.
Supplier collaboration in v1 is portal-based with email fallback.
Mobile app is out of v1 scope; responsive web is required.
Regional tax requirements must be configurable by locale.
All monetary values must be stored with amount, currency, and exchange-rate context.


# 3. Business Objectives
REQ-BIZ-001: Reduce maverick spend by enforcing catalog and approval policies before PO creation.
REQ-BIZ-002: Reduce requisition-to-PO cycle time from baseline median by at least 35 percent.
REQ-BIZ-003: Improve first-pass invoice match rate by at least 20 percentage points.
REQ-BIZ-004: Provide complete traceability from requester action to payment release decision.
REQ-BIZ-005: Standardize procurement workflows across entities while allowing localized policy controls.
REQ-BIZ-006: Provide real-time visibility into budget consumption by cost center and project.
REQ-BIZ-007: Improve supplier onboarding lead time through guided data collection and compliance checks.
REQ-BIZ-008: Reduce manual AP processing by supporting OCR and matching automation.
REQ-BIZ-009: Improve policy adherence by making policy checks visible at point of entry.
REQ-BIZ-010: Provide executive reporting for committed, accrued, and paid spend.
Objective fulfillment metrics are defined in {@success-metrics}.


# 4. Success Metrics and KPI Ownership
KPI-001: Median requisition approval turnaround time.
Target: <= 8 business hours for standard requests and <= 24 hours for high-value requests.
Owner: Procurement Operations Lead.
KPI-002: Percentage of spend with approved PO before invoice arrival.
Target: >= 92 percent within 2 quarters post-rollout.
Owner: Finance Controller.
KPI-003: First-pass three-way match rate.
Target: >= 80 percent for catalog-based goods invoices.
Owner: AP Manager.
KPI-004: User completion rate for requisition form without support intervention.
Target: >= 95 percent.
Owner: Product Operations.
KPI-005: Supplier onboarding completion within SLA.
Target: >= 90 percent completed within 5 business days.
Owner: Supplier Enablement Manager.
KPI-006: Data sync success rate to ERP connectors.
Target: >= 99.5 percent daily success, excluding customer-side outages.
Owner: Integration Operations.
KPI-007: Notification delivery success (email + in-app).
Target: >= 99 percent delivery, excluding invalid recipient addresses.
Owner: Platform Operations.

# 9. Permission and SoD Model
REQ-PERM-001: Access control must enforce tenant boundary at every API and query path.
REQ-PERM-002: Row-level restrictions must enforce legal-entity and cost-center scope.
REQ-PERM-003: Users cannot approve their own requisitions unless explicit emergency override is granted.
REQ-PERM-004: Users with invoice-entry rights cannot release payment batches without secondary approval.
REQ-PERM-005: Supplier profile bank detail changes require dual control and out-of-band verification.
REQ-PERM-006: Delegated approval must record delegator, delegate, reason, and effective date range.
REQ-PERM-007: Permission changes become effective within 2 minutes and invalidate stale sessions.
REQ-PERM-008: Emergency override usage requires mandatory incident ticket reference.
REQ-PERM-009: Data export rights are separate from dashboard view rights.
REQ-PERM-010: API tokens inherit least privilege scopes; wildcard write scopes are prohibited.
Permission model applies to all modules, including generated sections beginning at {@module-tenant-onboarding-functional}.


# 10. End-to-End Process Map
Step 1: User creates requisition with item, quantity, cost center, project, and needed-by date.
Step 2: Policy engine validates catalog compliance, budget availability, and mandatory fields.
Step 3: Workflow engine routes approval based on amount, category, and organizational hierarchy.
Step 4: Approved requisition converts to PO or release against frame contract.
Step 5: Supplier receives PO via portal and/or email.
Step 6: Receiving team records goods receipt or service entry.
Step 7: AP ingests invoice via OCR, EDI, portal upload, or email capture.
Step 8: Matching engine performs 2-way or 3-way match and assigns exception codes as needed.
Step 9: AP resolves exceptions or routes for dispute handling.
Step 10: Payment proposal is generated, reviewed, and approved.
Step 11: Payment status and remittance details sync to ERP.
Step 12: Reports update with committed, accrued, and paid spend states.
State machine baselines are defined in {@global-workflow-states}.

# 13. Global Form Standards
Every form must persist draft state every 30 seconds when data has changed.
Required fields must be marked with asterisk and included in top validation summary.
Field-level errors must appear inline and include actionable remediation text.
Date fields must store UTC with local display formatting.
Currency inputs must capture amount and currency code explicitly.
Amount precision: max 2 decimal places for currency, 4 for quantity conversions.
Lookup fields must support typeahead and keyboard navigation.
Attachment controls must enforce allowed file types and size limits.
Rich text fields must sanitize script tags and unsafe HTML attributes.
Phone fields must normalize to E.164 where country code is known.
Address forms must support country-specific postal code validation.
All form submissions require idempotency key to avoid duplicate creation on retries.


# 14. Master Data and Entity Model
Master entities: Tenant, Legal Entity, Department, Cost Center, Project, User, Role, Supplier, Item, Category, Contract.
Transactional entities: Requisition, Approval Task, Purchase Order, Receipt, Invoice, Match Case, Payment Batch, Support Case.
Relationship examples:
One Legal Entity has many Cost Centers.
One Supplier has many Banking Profiles with effective dating.
One Requisition can generate one or many Purchase Orders.
One Purchase Order has many PO Lines.
One PO Line can have many Receipts.
One Invoice can reference many PO Lines and many Receipt Lines.
One Match Case links one Invoice to many PO/Receipt artifacts.
One Payment Batch contains many Payment Instructions.
Entity dictionaries must include CreatedBy, CreatedAt, UpdatedBy, UpdatedAt, and SourceSystem metadata.


# 15. Data Governance and Stewardship
Each tenant must assign Data Stewards for Supplier, Item, and Cost Center domains.
Master data changes require reason codes when editing critical fields.
Critical fields include tax identifiers, bank account details, and payment terms.
Soft delete is prohibited for financial transaction entities.
Correction workflow must use versioning with previous values preserved.
Duplicate detection checks include fuzzy name + tax identifier + country match for suppliers.
Data import jobs must provide pre-validation report with blocking and warning categories.
Retention default for financial documents is 7 years unless tenant policy extends it.
Attachment retention follows document retention class.
Archived records must remain queryable for auditors with read-only access.


# 16. Security Baseline
All traffic must use TLS 1.2+ with HSTS.
Data at rest must be encrypted with cloud KMS-managed keys.
Authentication must support SAML 2.0 and OIDC for enterprise SSO.
MFA enforcement policy can be delegated to IdP with fallback local policy for break-glass accounts.
Session timeout default is 30 minutes idle, configurable up to 8 hours.
Privileged actions require step-up authentication challenge.
File uploads must pass malware scanning before becoming downloadable.
API keys must be hashed at rest and shown once at creation.
Security event logs must stream to SIEM integration endpoint.
Quarterly access review export must be available for compliance teams.


# 17. Privacy and Regulatory Constraints
PII must be classified and masked in logs and exported files unless authorized.
Field masking rules apply to personal phone, personal email, and bank account numbers.
Right-to-access requests must produce user profile and related activity export within configured SLA.
Right-to-erasure applies only where legal retention obligations do not override deletion.
Consent records for supplier communication preferences must be maintained.
Cross-border data transfer controls must support region pinning where contracted.
Tax and invoicing records must preserve immutable transaction trails.
Audit evidence exports must include hash references for attached documents.
Data processing addendum and subprocessors list must be visible in admin documentation.


# 18. Audit and Traceability Model
Every create, update, delete, approve, reject, and override action must emit an audit event.
Audit event payload includes actor, role, timestamp, tenant, entity type, entity id, changed fields, previous values hash, new values hash.
Audit events must be immutable and append-only.
Audit queries must support filters by actor, date range, module, and entity id.
Evidence packet generation must include signed event digest and linked attachments manifest.
Policy override events require ticket id and approver comment.
Integration-triggered events must identify source system and correlation id.
Bulk update actions must include child event expansion for each impacted record.
Audit API must support pagination and deterministic sorting.
Retention and export rules align with {@data-governance}.


# 19. Canonical Workflow States
Draft: Record is editable by creator and not yet submitted.
Submitted: Record is locked for key fields and awaiting workflow action.
In Review: Record is under active review or external validation.
Approved: Record passed required approvals and may trigger downstream creation.
Rejected: Record is closed as rejected with mandatory reason.
Returned for Changes: Record requires creator edits and resubmission.
On Hold: Processing paused due to external dependency or dispute.
Completed: Processing reached final successful business outcome.
Cancelled: User or system cancelled with reason and policy check.
Failed: Technical or business failure requiring operator intervention.
Modules can extend with domain-specific states but may not redefine semantics.
Transition rules and permission checks are module-specific.


# 20. Notification Principles
Notification channels: in-app, email, webhook callback.
SMS is optional and disabled by default.
Every notification template must have event trigger, audience rule, channel policy, and retry policy.
Critical finance events require at least two channels unless user opted out of non-essential emails.
Notification delivery attempts must be observable with status timeline.
Template versioning must preserve old render for already-sent notifications.
User-level quiet hours and digest mode must apply only to non-critical events.
Failure to deliver critical notification must raise operational alert within 5 minutes.
Notification catalog is enumerated in {@notification-catalog}.


# 21. Reporting Principles
Operational dashboards refresh every 15 minutes.
Financial reconciliation reports refresh hourly.
Ad-hoc exports support CSV and XLSX.
PDF export is supported for predefined executive packs only.
Report filters must include tenant, legal entity, department, and date range where applicable.
All report definitions must include metric formulas and source entity mappings.
Snapshot reports for period close must be immutable after signoff.
Scheduled reports support recipient groups and secure link expiration.
Comprehensive report inventory is listed in {@report-catalog}.


# 22. Integration Principles
Integrations use connector framework with pull, push, and event-driven patterns.
Supported transport: REST API, SFTP batch, message queue webhook callbacks.
All integrations require mapping profiles per tenant.
Sync jobs must expose run history, row-level errors, and replay controls.
Outbound calls use exponential backoff with idempotent request keys.
Inbound payloads must pass schema validation before persistence.
Reference data sync frequency must be configurable by connector.
Financial posting sync must guarantee ordering per legal entity and accounting period.
Connector packages are detailed in {@integration-packages}.


# 23. Release and Environment Strategy
Environments: Development, QA, Staging, Production.
Release cadence: biweekly minor releases, quarterly capability releases.
Feature flags must support tenant-level rollout and instant rollback.
Schema migrations must be backward compatible for at least one release cycle.
Release notes must identify changed modules, migration impact, and support playbooks.
Canary rollout is required for high-risk changes in matching and payments modules.
Production deployment window defaults to low-traffic regional times.
Hotfix process must include post-incident retrospective in support ops.


# 24. Assumptions and Dependencies
Customers provide accurate organizational hierarchy and cost center mappings.
Customers own IdP integration setup and user lifecycle policy.
Customers provide ERP connectivity credentials and testing windows.
OCR provider SLA is assumed at 99.9 percent monthly availability.
Email deliverability depends on customer domain SPF/DKIM setup for branded sending.
Tax engine integration requires maintained jurisdiction tables.
Supplier participation in portal workflows is assumed for at least 70 percent of spend.
Legacy open transactions are available for migration in agreed templates.
Data quality risks in source systems may delay go-live.
Dependencies are tracked in rollout governance and described in {@rollout-plan}.

Notify creator on submission, notify approvers on pending actions, notify creator on final decision.
Escalation notification after SLA breach by 4 business hours.
Digest mode allowed only for non-critical pending reminders.

Report rows must include legal entity, department, owner, and status dimensions.
## Integration Dependencies

# 25. Cross-Module Edge Cases
Edge Case EC-001: Supplier merged while open requisitions exist.
Expected behavior: Preserve historical supplier reference on old records; new transactions default to merged supplier id.
Edge Case EC-002: Budget reduced below already committed amount.
Expected behavior: Allow existing commitments, block new submissions, and alert budget owner.
Edge Case EC-003: Invoice arrives before receipt posting.
Expected behavior: Create match exception case with pending receipt follow-up.
Edge Case EC-004: User removed from IdP but still has active delegated approvals.
Expected behavior: Revoke access immediately and reroute tasks to fallback approver.
Edge Case EC-005: ERP connector outage during payment release window.
Expected behavior: Keep payment batch in approved-not-posted status and prevent duplicate release.
Edge Case EC-006: Duplicate invoice number across different suppliers.
Expected behavior: Allow if supplier differs; block if supplier + invoice number + currency + date window matches.
Edge Case EC-007: Fiscal period closed after requisition approval but before PO dispatch.
Expected behavior: Prompt requester to choose open period or request controller override.
Edge Case EC-008: Contract expires between requisition creation and approval.
Expected behavior: Revalidate contract linkage during approval and require renewal or alternate supplier.
Edge Case EC-009: Tax jurisdiction changes after invoice capture.
Expected behavior: Recompute tax estimate and flag variance for AP review.
Edge Case EC-010: Attachment malware detected after initial upload success callback delay.
Expected behavior: Quarantine file, redact preview links, and notify uploader + support ops.
